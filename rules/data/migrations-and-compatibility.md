# Migration、回填与兼容

## 迁移事实源

- 所有 PostgreSQL 结构变化进入 `backend/migrations/` 的版本化 Migration；已经在任何共享环境执行过的 Migration 不再修改、重排或复用版本号。
- 每个 Migration 写明目标不变量、锁风险、数据量假设、部署顺序、失败恢复和验证 SQL。ORM schema 只映射数据库，不替代迁移历史。
- 扩展、函数、触发器和索引方法属于显式基础设施依赖；Migration 在使用前检查可用性，并由受控数据库角色安装。

## 安全演进顺序

- 大表新增必填列采用“新增可空/安全默认 → 分批回填 → 验证无缺失 → 添加约束 → 应用切换”的 expand/migrate/contract 顺序。
- 新索引优先评估 `CREATE INDEX CONCURRENTLY`；它不能放在普通事务块中，Migration 工具需显式支持，并在失败时处理 invalid index。
- 添加外键或检查约束时，可先 `NOT VALID`，完成历史数据校验后再 `VALIDATE CONSTRAINT`，减少长时间阻塞。
- 回填按稳定主键分批，设置合理的 `lock_timeout`、`statement_timeout` 和节流；禁止单事务扫描并更新整张生产大表。
- 删除列、重命名字段或收紧类型前，先发布兼容读写版本并证明旧代码不再访问；破坏性 contract 步骤放到独立后续发布。

## 历史数据和种子

- 历史数据通过新的前滚 Migration、可审计回填任务或幂等种子收敛，禁止在 HTTP 热路径永久保留双读、双写和 legacy fallback。
- 种子使用稳定业务键和 `ON CONFLICT`/事务实现幂等，不覆盖用户可编辑字段，也不重置收藏、生成记录或审计事实。
- 无法自动判断的脏数据应让迁移停止并输出可审计清单，不能静默丢弃、伪造默认值或跳过约束。
- Down Migration 只在能无损恢复时提供；不可逆变更必须写明前滚修复和备份恢复边界，不能提供会丢数据的伪回滚。

## 验证门槛

- 在 PostgreSQL 18 上验证空库全量迁移、上一版本结构前滚、重复运行安全性、约束存在性和关键查询回读。
- 具有 Down 的迁移验证 up/down/up；不可逆迁移验证失败恢复和前滚修复路径。
- 涉及大表或约束的迁移，在接近真实数据量的副本上测量耗时、锁等待、WAL 增长和磁盘空间，不用小型内存夹具替代生产风险评估。
- 部署完成以 Migration 版本、schema 查询和业务回读为证据，不能仅依据命令退出码或应用启动成功。
